# B27 一页设计：自动暂停策略档位（保守 / 均衡 / 积极）

状态：APPROVED（用户 2026-11-09 批准三档策略，默认均衡；不再需要一页设计审批，合理阈值由 Agent 按 GameSim 现有信号自定；代码仍排在 B23 之后）。
来源：BACKLOG B27（R142 战术审计 + 用户提案）；本文件以前一版 `b27-timeout-tiers.md`（Luna，ffc247f）为底，触发规则一字未动，补上与 B23 的顺序和待用户定的问题——两份文件并存期间以本文件为准。
前提：只改托管助手（玩家方）的叫停灵敏度，不改 B3 的底线、不改 CPU。

## 现状（已核 sim.js 现有代码）

托管助手叫暂停只走 `maybeManagedCoach`，先过两道门：

- `assistantMayCallTimeout`：剩 > 4 才叫——即 B3 的「助手最多用 3 个、留 4 个给玩家」（`ASSISTANT_TIMEOUT_RESERVE = 4`，`js/engine/sim.js:99`）；快速模拟（`_quiet`）没有玩家，不保留。
- 两次叫停至少隔 85 秒（`_manageLastTo`）。

五个触发条件（固定概率，先命中先叫，`sim.js` 约 1830–1862 行）：

| # | 条件 | 概率 | 叫停理由 |
|---|---|---|---|
| 1 | 对方高潮（momentum ≥ 8 分） | 72% | 打断对方高潮 |
| 2 | 分差 ≥ 12（第 2 节起） | 48% | 分差拉开，重整阵脚 |
| 3 | 全队手感冰凉（avg hot ≤ −1.1）且落后 ≥ 3 | 42% | 手感冰凉，叫停调整 |
| 4 | 全员过劳（avgFat ≥ 72 且剩 ≥ 2 个） | 30% | 全员过劳，喘口气 |
| 5 | 末节关键分（第 4 节或第 3 节 < 200 秒，分差 4–14） | 40% | 关键分追分布置 |

普通失误**不是**触发条件（现在不是，B27 也不加）。CPU 对手有自己的一套（`maybeCpuManage` 的 ladder：高潮 65%、分差 + 体力 55%/40%、关键分 35%、末节体力 25%），B27 不动。

## 改动：一个档位设置

- 新增 `state.timeoutTier`，取值**保守 / 均衡 / 积极**，默认**均衡**；存在存档里，跟 `autoRotation` 同一套路（app.js state → GameSim）；UI 在托管设置里加三档选择。
- 档位只改「触发灵敏度」，**不改** B3 的留 4 规则、**不改**触发条件本身：

| 档位 | 概率 | 阈值变化 |
|---|---|---|
| 保守 | ×0.5 | 高潮 8→10 分、分差 12→14、过劳 72→78；末节关键分不触发 |
| 均衡 | 现状原样（数字一字不改，作为基线） | — |
| 积极 | ×1.5（封顶 0.9） | 高潮 8→6 分、分差 12→8、过劳 72→65；冷却 85→60 秒 |

- 实现：抽一个纯函数 `timeoutTierParams(tier)` 返回阈值 + 概率表（可单测，不依赖随机）；`maybeManagedCoach` 只读这张表，不再写死数字。

## 与 B23 的顺序

- B23（清掉战术加成的重复来源，Code 实现，用户 2026-11-05 选 B：并成单一来源、总量不变）同样改 sim.js 的平衡基线；**B27 的代码只在 B23 推上 main 之后再动**，避免两个人同时改 sim.js、也避免 B27 的定种子对比跑在旧基线上。
- B27 的定种子验收以前一版 B23 后的 main 为基线；若 B23 的落地数字有变，`timeoutTierParams` 的均衡档跟着 B23 走（均衡档 = B23 后的现状）。

## 验收（规则 10：定种子前后数）

- 单测：三档参数表各钉死；普通失误不触发叫停；B3 底线（剩 ≤ 4 不叫）三档都不破。
- 定种子对比：同一批种子跑三档 × 各 100 场快进：助手叫停次数 保守 < 均衡 < 积极；胜率波动在 ±2 个百分点内（档位是手感选择，不是强度选择）。
- 全量回归一次 + 浏览器看一眼托管设置三档能点、能存（一次视觉 QA）。

## 不做

不改 CPU 的 `maybeCpuManage`；不改 shout；不改暂停的体力回复；档位不进 online 对战（托管只在单人/生涯）。
