## 1. 一句话结论

**方向成立，第一段可做，全量不现实。**

- spec 的三条主线（快速开打 / 穿越 / 我的传奇）和"引擎唯一权威、选择≠必然结果、不破坏旧存档"
  这些原则，跟这个仓库现有的架构和习惯完全对得上，**没有需要推翻重来的地方**。
- 第一个可玩切片（M1 首页 → M2 快速开打 + 绝杀挑战 → M3 球场表现）**可行**，
  单人专注约 4–6 周。但 M2 比 spec 估的难：spec 说"加个最小适配器"，实测引擎**根本不兑现**
  玩家的出手人选择（见第 3.1 节），要动 `resolvePossession`。
- 2.0 全貌（穿越三职业 + 历史分支 + WNBA + 社交 + 经济）单人是**半年以上**的量，
  其中 WNBA（无数据、版权未定）和社交（需要账号/审核后端）**近期不可行**，只保留为研究项。

## 2. 设计分析：spec 好在哪、漏了什么

### 2.1 值得坚持的（照单全收）

1. **引擎唯一权威**：休闲模式不另写一套投篮模型。和 R33（多塔阵）、R130（神经刀）一路来的做法一致。
2. **选择≠必然结果**：策略改变的是出手分布和人选，不是命中率加成。这一条直接否掉了"+30% 关键球"之类的捷径。
3. **不破坏旧模式/旧存档**：本项目的存档已经踩过配额坑（R 系列存储修复），这条是底线。
4. **只读渲染**：渲染是模拟结果的投影，不写比分。现有 `CourtView` 已经基本是这么做的。
5. **分阶段、每阶段有闸门**：和我们 TASKS/WORKNOTE + 浏览器 QA + 变异测试的习惯契合。

### 3.1 G1 详解：为什么 M2 不是"加个适配器"

`scripts/research/clutch-choice-probe.mjs`（每行 1500 次，`8bd0fee`）：

| 局面 | 选中的人出手 | 三分出手率 | 头号出手人 |
|---|---|---|---|
| Q4 落后 1 分 10 秒，不选人 | 5% | 80% | 库里 43% |
| Q4，选伊戈达拉 + `pace_three` | **5%** | 78% | 库里 42% |
| Q2（无终场脚本），不选人 | 4% | 55% | 克莱 28% |
| Q2，选伊戈达拉 + `pace_three` | **5%** | 59% | 克莱 27% |

两层原因：

1. **终场脚本抢方向盘**：`applyLateGameScripts` 把 `offenseFocusId` 改成本队最佳三分手（`sim.js:2887-2891`、`:643-644`）。
2. **持球人≠出手人**：即使没有终场脚本，"指定持球人"也几乎不改变谁出手（和 R130 里发现的 Carmelo 打 35 分钟只投 6 次是同一类问题）。

好消息：引擎里**已经有一条现成通道**——终场追分需要三分时，`chase.shooterId` 会以 78% 概率直接把球交给指定射手（`sim.js:666-668`）。M2 的做法是让玩家决策写进这条通道并压过脚本，**不新增投篮模型**；剩下 22% 的"球没到他手里"（被包夹、失误、被迫分球）正好保留了"选择≠必然结果"。

**M2 的硬性验收**：用同一个探针，选中的人出手份额从基线 ~5% 提到和现有通道同一量级——
脚本今天把球交给库里时，库里占首个跳投的 ~43%（拿到球后仍可能突破、失误、分球），所以目标定在
**≥35%**（最终阈值在 ADR-002 里按实测定），同时命中率仍由 `calcMakeProb` 决定、没有必进、时钟不超支。

### M1 首页信息架构 + Play Now（P0A）

- **目标**：新玩家打开首页 5 秒内找到"快速开打"，一键进比赛；所有旧模式仍然能找到。
- **范围内**：
  1. ADR-001：`modeCatalog.js` 作为唯一事实来源，补齐 `legend`/`sandbox`/`duel`/`family-duel`，`homeTabs.js` 改为从目录派生（不再维护第二张表）。
  2. Play Now 主 CTA：一键 `autoFillTeam ×2` → 直接开打，跳过 setup 确认（setup 仍可从"自由对战"进入）。
  3. "快速演示"更名"快速开打"（id 仍为 `quick`）。
  4. Continue 面板统一以 root v3 为准，明确 legacy `peekSave` 的定位。
  5. 首页分组按 spec §3（挑战与竞技 / 经理生涯 / 自由创造 / 朋友一起玩），只有一个主 CTA；设计 token 收敛。
- **范围外**：引擎、存档结构、绝杀挑战、任何新模式逻辑。
- **验收**：单测——目录里每个模式 id 都在 DOM 里有入口、`validateCatalog` 通过、`homeTabs` 与目录一致；
  浏览器 QA——从首页点 Play Now 一次即进入比赛画面，所有旧模式卡可点击且进入原屏幕；首屏只有一个主 CTA。
- **估算**：3–5 天。

### M2 快速开打 + 绝杀挑战 MVP（P0B）

- **目标**：游客 15 秒内做出第一个关键决策，结果由引擎决定，想再来一局。
- **范围内**：
  1. ADR-002：玩家决策 vs 终场脚本的优先级规则（玩家决策写入 `chase.shooterId` 通道并压过脚本；只在显式开关下生效）。
  2. 引擎：最小改动让"出手人选择"被兑现（见 3.1）；为"突破"补最小 `meta`（出手人 + 区域）。
  3. `initializeScenario()`（新）：构造合法的 Q4 局面并校验不变量（节、时钟、比分、球权、场上 5 人、统计一致），不篡改 `snapshot()`。
  4. `ClutchController`（新模块）：`READY → AWAITING_DECISION → RESOLVING → CONTINUING → COMPLETED`（+`FAILED/CANCELLED`），选择提交后锁定；`attemptId` 代际令牌防止重试后旧回调乱入。
  5. 1 个精选场景、首轮 2 个选项（第二局解锁第 3 个），风险用定性标签表达，不显示"胜率"。
  6. 结果页：比分、因果解释（基于真实事件）、重试、可选分享（复用 `endingShareCard.js` 的思路）。
- **范围外**：多场景库、蒙特卡洛 1 万次报告、RNG 注入、个人级实时操控。
- **验收**：探针基线 → 修后对比（选中出手人份额 ≥ ADR 阈值，暂定 35%；命中率仍由 `calcMakeProb` 决定，无必进）；
  不变量单测（时钟不为负、加时正确、三分追平≠获胜）；重试 10 次 + 中途切模式无残留定时器；
  **旧模式回归**：非 clutch 模式下引擎行为不变（全量测试 + 同参数分布对照）。
- **估算**：7–12 天。

### M3 球场表现第一期（P0C 第一期）

- **目标**：10 个球员看得清是谁、球在谁手里、球怎么传/投出去的。
- **范围内**：领域事件适配器（快照差分推导回合开始/换人/节末 + M2 已补的 meta）；统一动画队列（入队、取消、代际令牌，替换现有 3 路独立 rAF）；持球光环、移动轨迹、传球弧线、投篮反馈；减少动态效果开关的静态战术板回退。
- **范围外**：精灵小人（M3b，等美术决策）、个人操控、PixiJS（除非 DOM 实测到瓶颈）。
- **验收**：渲染只读测试（喂冻结快照，渲染不改模拟状态）；同一场比赛开/关动画比分完全相同；手机端帧率实测记录；`prefers-reduced-motion` 生效。
- **估算**：8–12 天。

### M4–M8（闸门之后，届时展开细化）

- **M4**：先做存储预算与迁移链（v3→v4 可逆、旧存档夹具测试），再做身份 schema（出生地/家乡/代表地区分离、默认不公开）+ 捏脸（复用 `avatarArt.js`，合并球员生涯 P1）。家乡只影响叙事，不影响能力值。
