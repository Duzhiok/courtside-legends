## 一、架构决策（ADR）

### ADR-001：模式目录单一事实来源

- **状态**：PROPOSED（默认：是）
- **决策**：`js/data/modeCatalog.js` 是模式列表的唯一权威数据源；`js/ui/homeTabs.js` 从目录派生展示分组，不再维护第二张手写的模式映射表。
- **依据**：`BASELINE_AUDIT.md` §1.1/§1.2——目录缺 `legend`/`sandbox`/`duel`/`family-duel` 四项，且 `homeTabs.js` 现有分组与目录本身的分组**不一致**（例如 `players` 组在 homeTabs 里只有 `ranked`，但目录里没有这个分组概念），两套事实来源已经在漂移。
- **影响范围**：M1（P0A）。
- **替代方案考虑过的**：保留 `homeTabs.js` 独立维护，只是手动同步两处。否决理由：历史已经证明"手动同步两处"会漂移（现状就是证据），不是假设性风险。

### ADR-002：玩家决策 vs 终场脚本的优先级规则

- **状态**：OPEN（阻塞 M2b 开工；有建议方向，但最终阈值需要实现后用探针脚本实测确认，不能只靠讨论拍板）
- **背景事实**：`BASELINE_AUDIT.md` §2.3/§9，以及本文件配套的 `BASELINE_AUDIT.md` §0 复核（2026-11-03 在当前 HEAD 上重新跑了探针脚本）——玩家选中的出手人，无论有没有终场脚本介入，出手份额都停留在基线 ~5%（不选也是 5%）。终场脚本会把 `offenseFocusId` 强行改写为球队最佳射手（`sim.js:2887-2891` 附近，行号见 `BASELINE_AUDIT.md` §0 的漂移说明）。
- **建议方向（默认）**：玩家在绝杀场景做出的选择，写入引擎已有的 `chase.shooterId` 通道（终场追分需要三分时 78% 概率把球直接交给指定射手，`sim.js:666-668`），并让这条通道在"玩家已显式选择"时以该玩家选的人为目标，压过脚本默认挑选的"全队最佳射手"逻辑。
- **不采用**：新建一套独立的"玩家出手人覆盖"投篮模型——会违反 spec 的"引擎唯一权威"原则（`ROADMAP.md` §1 列为"照单全收"的设计原则之一），也会制造第二套需要单独维护平衡的命中逻辑。
- **验收阈值**：选中出手人份额从基线 ~5% 提升到 ≥35%（参考依据：脚本把球交给最佳射手时该射手本身约占 43% 的首个跳投份额）。**这个数字是起点，不是锁死的，最终以 M2b 实现后的探针实测结果为准**，但不应该低到和基线没有可感知差异（<20%），也不应该高到接近 100%（等于变相"必进选中的人"，违反"选择≠必然结果"）。
- **待你确认**：是否认可"复用 `chase.shooterId` 通道"这个技术方向？是否接受 35% 作为验收起点（而不是更高或更低的数字）？

### ADR-003：拆分 spec 的 P0B 为 M2a（一键开打）/ M2b（绝杀挑战）

- **状态**：PROPOSED（默认：是，已在 `ROADMAP.md` 按此拆分写入）
- **决策**：spec §14 把"一键开打"和"1 个绝杀场景"合并成一个里程碑；本次 roadmap 重组按你这次任务描述的措辞（P0B 只提 Quick Play/onboarding，P0C 单独是 Clutch Challenge/GameSim），正式拆成两个独立里程碑 M2a（P0B）/ M2b（P0C）。
- **依据**：`BASELINE_AUDIT.md` §2.3/§9 证实"一键开打"是低风险 UI 路由改动（`quick` 模式本就不校验账号），"绝杀挑战"需要改 `resolvePossession` 这个被所有模式共用的核心函数，风险量级完全不同。
- **影响范围**：M2 的编号拆分为 M2a/M2b；`docs/TASKS.md`/`docs/WORKNOTE.md` 后续记录里程碑进度时请使用新编号，避免和旧的"M2"产生歧义。
- **待你确认**：是否同意这个拆分？如果你坚持按 spec 原样一个里程碑做完再验收，告诉我，我会把 M2a/M2b 合并回单一 M2 小节（工作量不变，只是验收门合并，风险也合并）。

### ADR-004（占位）：存档版本升级策略 `schemaVersion` 3→4

- **状态**：OPEN（阻塞 M4 开工，当前只是占位，细节留到 M4 门控打开时补）
- **背景事实**：`BASELINE_AUDIT.md` §4.1——`validateRoot` 对 `schemaVersion` 高于或低于当前 `ROOT_SAVE_VERSION`（3）**直接拒读**，没有逐版本迁移函数；`migrateLegacySaves` 只处理 v1 legacy key 向 v3 的搬运，不是通用迁移链。
- **需要在 M4 开工前明确的问题**：升到 v4 时，v3 存档是直接判"旧版本不支持"（会报废老玩家存档，违反 Master Spec 的"不破坏旧存档"底线），还是写一个 v3→v4 的迁移函数（给新字段填缺省值）？本文档默认建议后者，但具体迁移函数设计留到 M4 门控打开后再细化。
