## 一、架构决策（ADR）

### ADR-001：模式目录单一事实来源

- **状态**：✅ APPROVED（2026-11-04）
- **决策**：`js/data/modeCatalog.js` 是模式列表的唯一权威数据源；`js/ui/homeTabs.js` 从目录派生展示分组，不再维护第二张手写的模式映射表。
- **依据**：`BASELINE_AUDIT.md` §1.1/§1.2——目录缺 `legend`/`sandbox`/`duel`/`family-duel` 四项，且 `homeTabs.js` 现有分组与目录本身的分组**不一致**（例如 `players` 组在 homeTabs 里只有 `ranked`，但目录里没有这个分组概念），两套事实来源已经在漂移。
- **影响范围**：M1（P0A）。
- **替代方案考虑过的**：保留 `homeTabs.js` 独立维护，只是手动同步两处。否决理由：历史已经证明"手动同步两处"会漂移（现状就是证据），不是假设性风险。
- **实施（M1，2026-11-03）**：目录补齐至 13 项（新增 legend/sandbox/duel/familyDuel；每模式带 `homeTab`/`exploreGroup`），`homeTabs.js` 改为从目录派生，Play Now 主 CTA 一键直进比赛，Continue 面板以 root v3 为准（有 root 生涯时隐藏 legacy 条），设计 token 收敛到 `css/tokens.css`。B10 色板决策（海军蓝 vs 深绿）仍待产品拍板，当前值沿用深绿 + 金色（spec §4.1），届时只改 token 一处。

### ADR-002：玩家决策 vs 终场脚本的优先级规则

- **状态**：✅ APPROVED WITH MODIFICATIONS（2026-11-04，方向批准；≥35% 仅为实验性起点，见文末审批记录）。M2b 开工前仍需单独的实现契约 + 模拟测试定义。
- **背景事实**：`BASELINE_AUDIT.md` §2.3/§9，以及本文件配套的 `BASELINE_AUDIT.md` §0 复核（2026-11-03 在当前 HEAD 上重新跑了探针脚本）——玩家选中的出手人，无论有没有终场脚本介入，出手份额都停留在基线 ~5%（不选也是 5%）。终场脚本会把 `offenseFocusId` 强行改写为球队最佳射手（`sim.js:2887-2891` 附近，行号见 `BASELINE_AUDIT.md` §0 的漂移说明）。
- **建议方向（默认）**：玩家在绝杀场景做出的选择，写入引擎已有的 `chase.shooterId` 通道（终场追分需要三分时 78% 概率把球直接交给指定射手，`sim.js:666-668`），并让这条通道在"玩家已显式选择"时以该玩家选的人为目标，压过脚本默认挑选的"全队最佳射手"逻辑。
- **不采用**：新建一套独立的"玩家出手人覆盖"投篮模型——会违反 spec 的"引擎唯一权威"原则（`ROADMAP.md` §1 列为"照单全收"的设计原则之一），也会制造第二套需要单独维护平衡的命中逻辑。
- **验收阈值**：选中出手人份额从基线 ~5% 提升到 ≥35%（参考依据：脚本把球交给最佳射手时该射手本身约占 43% 的首个跳投份额）。**这个数字是起点，不是锁死的，最终以 M2b 实现后的探针实测结果为准**，但不应该低到和基线没有可感知差异（<20%），也不应该高到接近 100%（等于变相"必进选中的人"，违反"选择≠必然结果"）。
- **待你确认**：是否认可"复用 `chase.shooterId` 通道"这个技术方向？是否接受 35% 作为验收起点（而不是更高或更低的数字）？

### ADR-003：拆分 spec 的 P0B 为 M2a（一键开打）/ M2b（绝杀挑战）

- **状态**：✅ APPROVED（2026-11-04）
- **决策**：spec §14 把"一键开打"和"1 个绝杀场景"合并成一个里程碑；本次 roadmap 重组按你这次任务描述的措辞（P0B 只提 Quick Play/onboarding，P0C 单独是 Clutch Challenge/GameSim），正式拆成两个独立里程碑 M2a（P0B）/ M2b（P0C）。
- **依据**：`BASELINE_AUDIT.md` §2.3/§9 证实"一键开打"是低风险 UI 路由改动（`quick` 模式本就不校验账号），"绝杀挑战"需要改 `resolvePossession` 这个被所有模式共用的核心函数，风险量级完全不同。
- **影响范围**：M2 的编号拆分为 M2a/M2b；`docs/TASKS.md`/`docs/WORKNOTE.md` 后续记录里程碑进度时请使用新编号，避免和旧的"M2"产生歧义。
- **待你确认**：是否同意这个拆分？如果你坚持按 spec 原样一个里程碑做完再验收，告诉我，我会把 M2a/M2b 合并回单一 M2 小节（工作量不变，只是验收门合并，风险也合并）。

### ADR-004（占位）：存档版本升级策略 `schemaVersion` 3→4

- **状态**：✅ APPROVED IN PRINCIPLE（2026-11-04）。详细迁移契约草案：`docs/implementation/ADR-004-migration-contract.md`（PROPOSED，2026-11-10，待评审）；M4 开工前必须评审批准。
- **背景事实**：`BASELINE_AUDIT.md` §4.1——`validateRoot` 对 `schemaVersion` 高于或低于当前 `ROOT_SAVE_VERSION`（3）**直接拒读**，没有逐版本迁移函数；`migrateLegacySaves` 只处理 v1 legacy key 向 v3 的搬运，不是通用迁移链。
- **需要在 M4 开工前明确的问题**：升到 v4 时，v3 存档是直接判"旧版本不支持"（会报废老玩家存档，违反 Master Spec 的"不破坏旧存档"底线），还是写一个 v3→v4 的迁移函数（给新字段填缺省值）？本文档默认建议后者，但具体迁移函数设计留到 M4 门控打开后再细化。

### ADR-005：Player Reborn（穿越·球员）实现方案与里程碑

- **状态**：✅ APPROVED（2026-11-04，产品负责人"按照你的推荐继续"，Q1–Q4 全部取默认值）。按 Q3，PR1 在 M3 闸门批准后开工；PR4 仍门控于 M2b。
- **全文**：`docs/implementation/ADR-005-player-reborn.md`
- **要点**：首个切片 = 1996 → 随机命运 → 替补 → 训练 → 争取上场时间 → 关键回合接管 → 职业结算（PR1–PR5）；新代码放 `js/reborn/`，教练和 GM 流程不改；历史源数据只读，改动存在可选字段 `root.reborn` 里；接管只走 M2b 的决策接口，PR4 门控是 M2b 完成；没有消费方的字段不加。
- **已批（默认值）**：Q1（用 v3 可选字段，不升 v4）、Q2（起点边界 = 季前）、Q3（Player MVP 放在 M3 之后、M4 之前）、Q4（随机命运 70% 历史 / 30% 虚构）。
- **编号提示**：本文 D7 指的是"穿越三种身份"；`CAREER_LIFE_ROADMAP.md` 里也有一个 D7（新秀成长跟随真实轨迹），两者无关。引用时请写成"DECISIONS D7"或"教练路线图 D7"。


### ADR-007：传奇宇宙（未来新秀用真实人物）+ 四分线 + 2050 终局与终身勋章

- **状态**：✅ APPROVED WITH MODIFICATIONS（2026-11-06）。修改项：重生每人一次、历史低频/幻想高频；成长不被历史封顶；Original Reborn = 玩家自建角色，另加 Legendary Reborn；Career Retirement 与 Lifetime Finale 分开；四分线 2035 只是可配置假设。Q3（头条名额）、Q6（跨界授权）仍 OPEN。
- **全文**：`docs/implementation/ADR-007-legendary-universe.md`
- **要点**：现在 2025 年后的选秀已经在用虚构球员补位（`leagueDraft.js` 的 `generatedProspect`），这就是替换点。按真实节奏 2026–2049 需要约 1,440–1,800 名新人，策展人物（国际传奇 / 先驱 / 跨界）只有几十到几百人，所以 **NBA 球员跨时代重生要当主力并默认开启**（4,393 人、数据全），策展人物做头条。勋章在任何合法生涯结束时都发，不只 2050——1996 年入行的教练 2031 年就到 70 岁强制退休了。勋章档次复用 `legacy.js` 的分档，存账号层 `LegacyArchive`。四分线是存档内联盟规则，关闭时 M2b-0 金标哈希必须不变，另写 GameSim ADR，排在 M2b-1 / M3 之后。

### ADR-008：首页四空间导航 + 离线托管联赛

- **状态**：✅ APPROVED IN PRINCIPLE（2026-11-06）。中文名"我的篮球人生"；托管 20 场/天为原型上限，**金币和 XP 同时递减**（1–5 场 100%/100%，6–10 场 50%/50%，11–20 场 0%/25%，待平衡）；N-1 导航骨架作为 Navigation-Only 例外可先于 M2b-1；Q4（广告）、Q6（阵容合一）未定。
- **全文**：`docs/implementation/ADR-008-navigation-four-spaces.md`
- **要点**：我的世界 / 我的球队 / 传奇生涯 / 自由球场。补上模板缺的一级「传奇生涯」（Reborn + Franchise）。第一阶段只把 `modeCatalog.homeTab` 从 3 个值改成 4 个，可回退、不动存档。托管"场数宽松、奖励封顶"：20 场/天，前 5 场全额金币、6–10 场半额、之后只产故事；用 `GameSim({ rng })` 按 `hash(账号, 日期, 场次)` 固定结果，刷新不能重掷；不计入排位和联机奖金。已发现两套"我的阵容"（本地卡 vs 联机服务端账号），合一另写 ADR。不做广告位；没有后端前不显示假的社交数字。

## 五、2026-11-04 审批记录（产品负责人原话要点，作为上面状态变更的依据）

**批准方向 ≠ 批准所有实现细节。** ADR-002 的概率阈值是实验性验收指标；ADR-004 的迁移细节尚未技术审查。

### ADR-002 修改条件
- 复用现有 `chase.shooterId`，但**不把 78% 球权分配倾向当成必然出手**。
- 优先级：玩家关键球决策 > 自动终场脚本 > 默认战术。
- 保留现有投篮、防守、失误、体能、回合结算机制。
- 选"三分"必须影响真实的三分进攻策略，而不只是换出手人。
- 禁止硬编码命中率或必然结果。
- ≥35% 选中出手人份额 = 初始实验目标，以基线实测和模拟验证为准。
- 分开度量：选中人出手份额、三分出手率、失误率、胜率。
- 普通模式不受影响。

### ADR-004 修改条件
- 引入 schemaVersion 4 时，**不得拒读或丢弃合法的 v3 存档**。
- 版本化迁移：迁移前备份；确定性 v3→v4 转换；提交前校验；失败可恢复。
- 测试：现有存档、缺字段、损坏数据、重复迁移。

### D7 修订
穿越必须最终支持三种身份：
1. **历史穿越**——接管一名真实历史球员（必做能力，不是可丢弃的点子）；
2. **原创穿越**——虚构球员插入历史世界（MVP 可先做这个）；
3. **随机命运**——随机获得历史或虚构身份。

保留不可变的历史源数据；玩家改动存进隔离的平行时间线；防止重复身份和名单不一致；公开发布前审查真实球员肖像/授权。

### 执行规则
1. Master Spec 冻结为 **v1.0 产品基线**；新想法进 Backlog，不插入当前 Sprint。
2. 顺序：M1 首页 → M2a 一键开打 → M2b 绝杀挑战 → M3 2D 接管 → M4 My Legacy/存档升级 → Reborn 与长期生态。

4. 不同时实施多个大里程碑；不静默删除已批准功能；保留全部现有模式、数据、存档。

## 八、2026-11-06 产品负责人追加裁决

### 未来选秀与候选池
- **76 人 = 每届 Draft Candidate Pool 默认规模**，不是全部进入 NBA。实际选中人数由球队数和轮次决定（30 队两轮 = 60 个顺位），其余成为落选秀或自由球员。
- **位置：软约束，不设硬配额。** 候选池位置分布参考历史数据、每届允许波动；联盟检查长期阵容健康；多位置球员（PF/C、SF/PF）可缓解单一位置不足。"中锋 20%"只作为容量测试的参考场景。
- **静态容量够 ≠ 实际模拟不缺人。** 76×24 = 1,824，可用 3,519；仍需验证：对应年份的重生资格、是否已在当前时间线出现、选秀管线能否处理混合数据。
- 头条传奇：先 2 人、最多 4 人/届，待平衡参数。
- 跨界名人：公开发布前逐项核查，未获授权不公开使用。
- **真实人物重生不自动解决授权**：现有数据库中的球员姓名、照片和形象同样纳入公开发布前的权利审查。
- 广告位：暂不做。本地与联机阵容统一：独立 ADR，不放进 N-1。重生潜力上限：暂不定数值，先做能力分布和成长模拟。四分线：保留 2035 可配置假设，M3 后单独设计。

### M2b-1
- 份额：选 (b) 校准；45–70% 为**第一轮实验区间**，之后按战术类型与防守场景校准，不是永久规则。优先调决策专用分球权重；若影响普通比赛，用独立的 Clutch Decision 参数。
- 重复提交：`already_armed`；以后若要改决定，用显式 `replaceDecision()`。
- 事件契约测试：必须补。
- **执行结果（R161）**：`already_armed` 与契约测试已完成；**校准被一个新设计问题挡住**（选中接球型角色球员会降低其份额），见 `M2b-clutch-decision-design.md` §11。

### My World MVP（ADR-008 内部任务，不另设里程碑）
- 立即做轻量但真实可用的"我的篮球人生"：My Identity（昵称/家乡/简介，持久化）、My Journey（复用现有存档与继续入口）、My Legacy（真实成就，空状态如实）、My Home（静态 CSS/SVG 房间，不做房产经济）、Community Feedback（真实渠道或可复制模板，不做空按钮）。
- **账号身份 ≠ Reborn 职业身份**，互不覆盖；复用账号系统，只加必要资料字段。
- 分 N-1a（导航 + 页面骨架）/ N-1b（真实数据）/ N-1c（My Home + 反馈）。不做 Auto League、社交后端、复杂捏脸、广告、四分线、新经济。
