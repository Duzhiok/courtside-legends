# T6 真联机对战 — 设计文档（R57 设计，R60 实现 P0）

> 状态：P0 已实现（2026-10-24，见 WORKNOTE R60），P1–P3 待排期。核实基线：2026-10-24，main 8f3d80b。
> P0 不动现有单机流程；联机是新增模式（`online.html` + `server/`）。

## 1. 现状约束（已核实）

- 项目是纯前端静态站（ES 模块，无构建/后端）；账号只在 localStorage。
- `js/engine/sim.js` 是纯 JS：无 document/window/localStorage 代码引用（仅快照注释提到 localStorage），可直接跑在 Node 服务端。
- sim **非确定性**：47 处 `Math.random`，无种子。Lockstep（两端各跑一份 sim、只同步种子/指令）需要把全部随机点种子化，改动面大。
- sim 已有现成同步原语：`snapshot()`（`sim.js:183` 起注释“Snapshot mutable sim state”）+ 从数据恢复（`sim.js:240` 起的 load 路径，含教练计划、动量、托管开关、伤病开关的恢复）；tick 驱动，每 tick 调 `onTick(snapshot)`（`sim.js:403/414/469/540/547`）。
- 客户端教练输入面：战术/焦点、换人、暂停、轮换设置、托管开关（autoOffense/autoDefense/autoRotation）。
- 客户端已有恢复接线：`wireRestoredSim(sim, homeTeam, awayTeam, youSide)`（`app.js:1328`，在 1396 被恢复流程调用）——服务端快照能否直接喂给它，是 P0 前必须实测的第一项。
- 速度档：`sim.speed` clamp 在 1–3（`sim.js:138`），`_loop` 在 359 行起。

## 2. 架构决策：服务端权威，不做 lockstep

- 服务端跑唯一一份 sim，每 tick 向双方广播 snapshot；客户端只发决策指令（换人/战术/暂停/托管开关），不跑 sim。
- 放弃 lockstep 的理由：47 处随机点种子化 + 两端浮点一致性验证成本高，且收益（省带宽）不值得；快照同步直接复用现有 `snapshot()/load()`，改动最小。
- MVP 对局类型：**纯对决（沙盒/选秀阵容），不带生涯经济**。生涯金币/市场/存档联机是 P3 之后的事。

## 3. 同步模型

- 传输：WebSocket（Node + ws，与现有 ES 模块同构，sim 代码服务端零改动复用）。
- 节奏：服务端 tick 即现有 `_loop` 节奏；广播全量 snapshot 起步，实测快照体积后再做差量（快照含两队全员状态，体积需实测，目标单包 < 8KB，否则拆“比分/时钟/球权”高频字段 + “球员状态”低频字段）。
- 决策窗口：换人/暂停只在死球或节间生效（复用现有教练事件机制）；指令带 tick 序号，服务端校验合法性（轮换内球员、暂停次数、当前可操作方）后执行，非法指令回错误不中断对局。
- 延迟处理：客户端本地预测只做 UI（按钮状态），比分/时钟永远以服务端快照为准；一方掉线 30 秒内可重连（服务端重发最新快照 + 双方阵容）。
- 协议草案（P0）：`hello`（房号 + 账号名）→ `joined`（双方阵容）→ `snapshot`（服务端 → 双方，每 tick）→ `decision`（客户端 → 服务端，带 tick 序号）→ `decision_rejected`（非法指令）→ `game_over`（终场快照 + 战报）。

## 4. 账号与匹配（MVP 从简）

- P0 不做服务端账号：房号制（创建房间得 6 位房号，对方输入房号加入），与现有 localStorage 账号名并列显示。
- P1：断线重连 + 观战（第三个连接只收快照，不发指令）。
- P2：匹配池（按 OVR 区间排队）+ 战绩本地记录。
- P3：服务端账号、排位分、生涯联机经济。

## 5. 反作弊

- 服务端是唯一事实源：客户端改本地数据无效；指令合法性在服务端逐条校验；比分/球员属性永不信任客户端。
- 房间制 MVP 下作弊面小（改本地只影响自己屏幕），P2 匹配池上线前补服务端速率限制与对局结果签名。

## 6. 分阶段

- P0：Node 服务端（跑 sim + 广播快照）+ 房间创建/加入 + 决策指令通道 + 1v1 全流程可玩。
- P1：断线重连、观战、快照差量压缩。
- P2：匹配池、战绩、重赛。
- P3：账号、排位、生涯联机。

## 7. 动手前待实测（P0 第一个任务）

1. snapshot 序列化后体积（两队 12 人满编时）。
2. 服务端 tick 间隔与现有 `_loop` 速度档（1–3）如何映射到广播频率。
3. 客户端现有 `wireRestoredSim` 能否直接消费服务端快照（即 load 路径是否覆盖快照全部字段）；若有缺口，先补 load 路径再接联机。
4. 决策指令在死球/节间窗口的排队语义（现有教练事件机制是否已满足，还是需新增队列）。

### 7b. P0 实测结论（R60，设计文档的四项全部落地）

1. **体积**：`snapshot()` 实测 ~70KB（名单三倍重复），P0 改发精简帧（`server/online-frame.mjs`，< 8KB），静态球员数据由 `joined` 一次给齐。差量压缩推迟到 P1（精简帧已够小）。
2. **节奏**：服务端固定速度 2（300ms/回合，整局约 60 秒）；速度选择是 P1 可选项。
3. **`wireRestoredSim` 不能直消费快照**（它要活 sim 实例），但 paint 函数全是快照驱动的——P0 客户端（`js/online/client.js`）按这个思路自己渲染，不复用 `wireRestoredSim`。
4. **窗口**：无需排队队列——换人立即生效（下回合起用新名单），暂停/节间/中场天然停住且对双方开放调整；任一方可恢复，20 秒无人操作自动恢复（断线座位在场时不自动恢复）。
5. **引擎缺口（实测新增）**：战术/持球人/站位原本只对我方生效，P0 给它们加了 `sideKey`（单机默认路径不变）；防守体系与托管仍是单方模型，**不在 P0 决策集内**，是 P1 的引擎工作。

## 8. 非目标（P0 明确不做）

- 不改单机流程、不动生涯经济、不做服务端账号、不做 lockstep、不做客户端 sim 预测比分。
