# 3D 实时播报方案（DRAFT 草稿，只规划，不写代码）

> 状态：草稿，未实施。写于 2026-10-28。只规划，不动游戏代码；
> 实施前由 Luna review，并由用户确认第 8 节的开放问题。
> 游戏本体：场边传奇 · Courtside Legends（纯静态网页游戏）。

---

## 0. 一句话

给现有的事件驱动模拟加一层 **3D 演出**，不把游戏重写成 3D 物理游戏。
模拟继续按回合结算出结果（投进 / 打铁 / 暴扣 / 失误），3D 视图负责把
结果“演出来”。这是一个**表现层升级**，不是引擎替换。

## 1. 核心定位（先说实话）

- **模拟不是物理模拟**。`js/engine/sim.js` 的 `resolvePossession()` 按回合
  算出结果，`emit(type, text, meta)` 把事件推给界面；它不产出任何球员的
  真实移动轨迹。3D 小人不可能“真的跑战术”。
- **所以 3D 里的移动是示意性的**：球员在战术站位点之间滑过去（glide），
  到位后播一个固定动作（投篮 / 扣篮 / 盖帽 / 抢断各一个 canned 动画）。
  看起来像转播，本质是动画演出。这个预期必须先对齐，否则做出来会觉得“假”。
- **什么都不动**：模拟逻辑、卡牌数据、评分、战术系统全部原样。
  3D 只读两样东西——每回合的快照（`snapshot()`）和事件（`meta`），
  和现在 2D 的 `CourtView` 读的东西完全一样。

## 2. 现状盘点（方案的地基，全部来自实读代码）

### 2.1 现在的 2D 播报是怎么画的

`js/engine/court.js` 的 `CourtView`（478 行）是 **DOM + CSS**，不是 canvas：

- 球场是一个 `.fullcourt` div，线条、篮筐、罚球圈全是 CSS div
  （`ensureDom()`），球员是按百分比坐标定位的 token div。
- **位置模型已经存在，而且可以直接复用**：`SETS` 是 8 套战术站位
  （balanced / triangle / smallball / iso_heavy / grind / motion /
  pace_space / morale_boost），每套 5 个点，顺序固定是 C → PF → SF → SG → PG
  （从篮下到外线）；`lineupForSlots()` 按 `playPos / pos` 把场上五人对号入座；
  防守方用 `DEF_GAP` 偏移（站在进攻球员和自家篮筐之间）。
- `toCourt(slot, attackingUp, phase)` 把前场相对站位映射成全场百分比坐标：
  主队攻向顶端（`y=6` 是客队篮筐，`y=94` 是主队篮筐），`phase` 0→1 用约
  **2.6 秒**完成“后场发球 → 前场落位”的推进；落位后 token 带正弦/余弦微漂。
- 球跟着主控（`handlerSlotIndex()` 选 PG，fallback SG），不在谁手里就
  不乱跑；`_lastTokenPos`（key 是 `${side}-${playerId}`）记录每个 token
  的最后位置，供投篮弧线起手用。
- 两种 token 模式（`localStorage` 键 `courtside-simple-players`）：照片头像，
  或 CSS 小人（头 + 球衣躯干 + 手臂 + 腿，带摆动）。

### 2.2 事件是怎么流到播报的

`GameSim.emit(type, text, meta)`（`sim.js`）→ 构造时传入的 `onEvent` →
`js/app.js` 的 `handleSimEvent(e)`（约 L6832）：

- `e.meta.shot` → `state.court?.onShot(e.meta.shot)`；
- `e.type === "dunk"` 且 `e.meta.player` → `showDunkFlash(...)`（一个闪光 overlay）；
- 其他一律 `pushFeed(...)` 写文字战报 + `paintScore(...)` 更新比分。

**事件词表（实查，全量就这四种）**：

| 事件 | meta | 现在 2D 里干什么 | 3D v1 能干什么 |
|---|---|---|---|
| `score` | `meta.shot { shooterId, made: true, pts }`（仅跳投得分分支，`sim.js` L1175） | `onShot()` 播 750ms 弧线 | 3D 投篮弧线 + 入网 |
| `miss` | `meta.shot { shooterId, made: false, pts }`（仅跳投打铁分支，`sim.js` L1220） | `onShot()` 播 750ms 弧线 + 篮板弹 | 3D 投篮弧线 + 打铁弹框 |
| `dunk` | `meta.player { id, name, ... }` + label（`sim.js` L1112） | `showDunkFlash` 闪光 | 3D 扣篮动作（可保留闪光做 fallback） |
| `coach` | 无（43 处调用，全是文字） | 只写战报 | 不动，只写战报 |

**关键约束**：盖帽、抢断、篮板、犯规**没有独立事件类型、没有 meta**，
它们只出现在 `score` / `miss` / `coach` 的文字里。所以 v1 的 3D 动画只能
可靠地挂在投篮和扣篮两个钩子上；想要盖帽/抢断动画，必须给 `sim.js`
的 emit 调用**新增 meta 字段**（只加数据、不改结算逻辑，见 5.3b）。

### 2.3 回合节奏（动画时序的硬约束，见第 6 节）

`GameSim._loop()`：`step()` → `setTimeout(_loop, possessionDelay())`。
`possessionDelay()`（`sim.js` L508）：

| 速度 | 每回合墙钟时间 |
|---|---|
| 1x（真实） | 1100–3600ms（跟随比赛时钟消耗，约 150ms 墙钟 / 比赛秒） |
| 2x | 300ms |
| 3x | 85ms |

现在的 2D 投篮弧线是 **750ms**（`court.js` 的 `_shotFrame()`，`FLIGHT = 750`），
在 1x 下塞得进回合间隔，在 2x/3x 下已经靠“新事件到来就
`cancelAnimationFrame` 掐断旧弧线”硬扛。3D 必须继承同一条规矩（第 6 节）。

### 2.4 其他现成条件

- R85 刚把 `.court-wrap` 改成**固定高度**（不再是 `min-height`），左右栏
  各自内滚——3D canvas 挂进同一个 `#court-root` 容器时尺寸是稳定的，
  不需要额外处理 resize 抖动（仍需一个 `ResizeObserver` 做常规适配）。
- `package.json` 里**没有 three.js**（dependencies 只有 `ws`，devDeps 是
  Capacitor + eslint），且项目是零构建的纯静态站——依赖接入方式见 3.2。

## 3. 技术选型

### 3.1 用 Three.js，不用 Godot

- **Godot 意味着重写整个游戏**：模拟、卡牌、界面、存档全要搬进 Godot
  的工程和脚本体系，几个月的工作量，玩法上多不了一点东西。
  Godot 是给“从零做一个可实时操控的动作/3D 游戏”准备的，不是给
  “给现有网页模拟加一层 3D 演出”准备的。
- **Three.js 直接嵌进现有网页**：游戏还是 HTML/CSS/JS，3D 只是一个
  挂在 `#court-root` 里的 WebGL canvas；模拟、卡牌、界面、存档、
  GitHub Pages / itch.io / Capacitor 壳子全部原样工作。
- 只有当用户将来要做**另一款**游戏——能用手柄/摇杆实时操控球员的那种——
  才轮到 Godot 上场。那是新游戏，不是这个视图升级。

### 3.2 依赖接入：vendoring，不要 CDN

- 项目零构建，没有打包器。Three.js 用官方 ES module 构建
  （`three.module.js`，约 600KB–1MB），**固定一个版本号、直接放进仓库**
  （例如 `js/vendor/three.module.js`），页面用 `import` 引用。
- 不用 CDN import map 的原因：Capacitor 壳子里的页面跑在本地文件上下文，
  离线或弱网时 CDN 会断；itch.io 的 zip 也要求资源自包含。
  vendoring 后 zip 从约 12MB 涨到约 13MB，仍在 itch 限额内。
- 版本号一旦定下就不要随便升（Three.js API 经常变），升级单独做一次
  回归验证。

### 3.3 坐标映射：百分比坐标直接换算

现有百分比坐标 → 3D 球场坐标（以 NBA 球场 28.65m × 15.24m 计，
`x` 是宽度轴，`z` 是长度轴，`y` 是高度轴）：

```
X = (x - 50) / 50 * 7.62        // x: 0–100 → -7.62–+7.62
Z = (y - 50) / 50 * 14.33        // y: 0–100 → -14.33–+14.33
```

- `y=6`（客队篮筐）→ `Z ≈ -12.6`，`y=94`（主队篮筐）→ `Z ≈ +12.6`，
  与现有“主队攻向顶端”的约定一致：3D 里远端是客队篮，近端是主队篮。
- 映射函数必须是**纯函数**（输入百分比、输出三维坐标），这样它可以在
  Node 测试里直接测，不需要 WebGL（见第 9 节）。
- 2D 里“高度用球的大小假装”（`_shotFrame()` 里球从 12px 胀到 20px 再缩回）
  在 3D 里不再需要：高度就是真实的 `y` 轴，投篮弧线是同一条贝塞尔曲线
  加上真实的抛物线高度。

## 4. 球员模型：程序化小人，不要真人模型

- 每个球员 = 代码生成的低多边形小人：胶囊躯干 + 球头 + 手臂 + 腿，
  **队服颜色 + 背号**（背号用 canvas 纹理画在躯干上，一次生成、复用）。
- 零美术资产：不用买模型、不用绑骨骼、不用处理肖像权（小人不像任何真人，
  只有队服色和号码——这也是公开上架时最安全的形态）。
- 名字用悬浮文字牌（canvas 纹理的 sprite，始终朝向镜头），内容和 2D
  的 `tok-name` 一致（简称 + 实时得分）。
- 肢体摆动直接复用现有思路：2D 的 CSS 小人已经有摆动逻辑，
  3D 里改成程序化关节旋转（跑动时手臂/腿正弦摆动，站立时微呼吸起伏）。
- 风格参考：不是写实，是“战术板小人立起来”的样子——干净、辨识度高、
  手机跑得动。更精细的模型（面部、肌肉、球鞋）明确不在 v1（第 7 节）。

## 5. 分阶段建设计划

### Stage 0 — 准备（小）

- `js/vendor/` 放入固定版本的 `three.module.js`；`index.html` 不需要改结构，
  只需给 `#court-root` 一个 3D 挂载点（与现有 `.fullcourt` div 并存）。
- 新文件 `js/engine/court3d.js`，导出 `CourtView3D` 类，**接口与 `CourtView`
  完全一致**：`render(snap)` + `onShot(shot)`。`js/app.js` 只在构造处分支
  （`state.court = use3d ? new CourtView3D(...) : new CourtView(...)`），
  `handleSimEvent()` 一行都不用改。
- 开关：`localStorage` 新键（例如 `courtside-3d-view`），按钮放在现有
  “人物：简易/照片”按钮旁边，文案“视角：2D / 3D”。

### Stage 1 — 场景 + 球场 + 10 个小人 + 球（**最大的一块**）

- 场景：球场地面（木地板色 + 白线，用现有 CSS markings 的尺寸比例换算）、
  两个篮架（篮板 + 篮筐 + 篮网简化成圆环 + 锥形线框）、灯光（一个主方向光
  + 环境光，先不做阴影；阴影是 Stage 5 的可选优化）。
- 10 个程序化小人 + 1 个球，位置**直接复用 `CourtView.render()` 的计算结果**：
  战术站位 `SETS`、对位 `lineupForSlots()`、防守偏移 `DEF_GAP`、2.6 秒推进
  `phase`、落位微漂——这些逻辑原样搬过来，只是输出目标从
  `el.style.left/top` 换成 3D 坐标（第 3.3 节的映射）。
- 验收标准：同一快照下，3D 站位和 2D 站位一一对应（战术切换、换人、
  攻守转换时小人跟着动）；球在主控手里；页面不报错。
- **为什么这是最大的一块**：它是地基——坐标系、模型生成、快照驱动、
  渲染循环全在这里搭完，后面每个阶段都只是往这个架子上挂东西。

### Stage 2 — 固定转播机位（小）

- 机位：球场侧面、高于地面、略带俯角的标准电视转播角，看向球场中心；
  攻守转换时不切镜头（v1 不做多机位、不做跟随特写）。
- 允许的唯一镜头动：2.6 秒推进阶段里极轻微的横向平移（跟随球过半场），
  幅度要小，避免晕眩；默认可以先完全固定，推镜作为可选项后加。
- 明确不做：自由镜头、鼠标拖拽旋转、缩放、第一人称（第 7 节）。

### Stage 3 — 固定动画，按事件播（第二大块）

按 2.2 节的事件词表，一次只做这几样：

| 触发 | 动画 | 时长预算 |
|---|---|---|
| `score` / `miss` + `meta.shot` | 投篮弧线：球从投手位置沿贝塞尔曲线飞向篮筐，带真实高度抛物线；进 = 穿网收缩，铁 = 篮板弹 + 落向中场方向（复用现有 `_shotFrame()` 的 made/miss 两段逻辑，只是从 2D 尺寸把戏换成真实 `y` 轴） | ≤750ms（与现有弧线一致） |
| `dunk` + `meta.player` | 扣篮：持球人滑向篮下 + 起跳 + 灌篮动作（躯干前倾、手臂上举、球入网）；现有 `showDunkFlash` 保留做 fallback（3D 关掉时仍有闪光） | ≤1000ms |
| 每回合落位后 | 待机：呼吸起伏 + 轻微重心晃动；推进阶段：跑动摆臂摆腿（正弦关节旋转，速度跟推进 `phase` 走） | 持续循环，不占事件预算 |
| 持球人 | 运球：球在持球人身边做小幅上下弹跳（`y` 正弦），球离手投篮时切换到弧线 | 持续循环 |

**3b（可选，排在 3 之后）：盖帽 / 抢断 / 篮板动画**。前提是给 `sim.js`
的 emit 调用**新增 meta 字段**（例如盖帽分支 `meta.block { blockerId }`、
抢断分支 `meta.steal { stealerId }`）。只加数据、不改结算逻辑、不改数值；
但这是唯一一处要碰 `sim.js` 的地方，需要单独 review，且可以整个砍掉
而不影响 3 的主线。

### Stage 4 — 2D / 3D 开关与回退（小）

- 默认 **2D**（现有视图），3D 是可选项；开关状态存 `localStorage`，刷新后保持。
- WebGL 不可用（老浏览器、被禁用的 WebGL、创建 context 失败）→
  自动回退 2D，并在按钮旁给一句提示，不报错、不白屏。
- 2D 代码**原样保留**，不删不改：它是 fallback，也是低端设备的默认路径。
  3D 出任何问题，用户一键回 2D 就能继续玩。

### Stage 5 — 移动端性能（中）

- `pixelRatio` 上限（例如 ≤2），小人面数压到最低（胶囊 + 球头合计
  每人 < 500 三角形），全场 10 人 + 球场 + 篮架总计 < 10k 三角形。
- 阴影默认关（或只开一个极 cheap 的 blob 阴影——脚下椭圆暗斑，不是真阴影）。
- 切后台 / 切回 2D 时暂停渲染循环（`cancelAnimationFrame`），不空耗电量。
- 低端机兜底规则：WebGL 创建失败 → 2D；帧率持续过低（例如连续 3 秒
  < 25fps）→ 提示用户切回 2D（不自动强制切，避免打断比赛）。
- 验收必须在真机上做：至少一台 iPhone（Safari + Capacitor 壳子里的
  WebView 各一遍）和一台中低端 Android，跑满一节（12 分钟比赛时间）
  不闪退、不烫到降频。

## 6. 动画时序约束（最容易翻车的地方）

**铁律：动画是战报的附庸，不是主角。战报不等动画。**

- 1x 下每回合有 1100–3600ms，750ms 的投篮弧线塞得进；2x 只有 300ms，
  3x 只有 85ms——任何动画都**不可能**在 2x/3x 下完整播完。
- 策略（继承现有 2D 的做法，并把它写成明规则）：
  1. **可打断**：新事件到来，当前动画立即取消（现有 2D 就是
     `cancelAnimationFrame(this._shotRaf)` 掐断旧弧线；3D 同理，
     取消当前 tween，球和小人直接跳到最新快照的位置）。
  2. **可压缩**：2x/3x 下动画按速度倍率加速（timeScale），或跳过中间过程
     只播结果（球直接出现在篮筐处、小人直接站在落位点）。
  3. **绝不排队**：动画不进队列等前一个播完。排队会在 2x/3x 下无限
     积压，视图越落越远——这是唯一不能接受的失败模式。
  4. **视图最多落后一个回合**：取消/压缩后，视图状态必须等于最新快照；
     任何时刻暂停，画面都应该是一张“合理”的比赛定格，而不是半截动画。
- 推进 `phase`（2.6 秒）同样处理：2x/3x 下按倍率压缩，落位点不变。
- 速度切换（`state.speed` 的 1x/2x/3x 按钮）必须同步切换动画 timeScale，
  不能出现“3x 速度下还在播 1x 动画”的错位。

## 7. v1 明确 OUT of scope

- 真人球员模型、面部、球衣细节、动作捕捉、外部动画文件。
- 自由镜头、鼠标拖拽 / 缩放、第一人称、回放系统。
- **可实时操控的玩法**（用摇杆控制球员打球）——那是另一款游戏，
  不是这个视图升级；真要做那个，再谈 Godot。
- 模拟逻辑、卡牌数据、评分、战术系统的任何改动（3b 的 meta 字段除外，
  且只是加数据）。
- 新美术资产、音效、解说语音。
- 2D 视图的删除或重构（2D 是永久 fallback）。

## 8. 开放问题（等用户定）

1. **小人风格**：A) 极简胶囊小人（最快、最稳、手机最友好）；
   B) 稍精细一点的低多边形小人（带球衣号码、肤色区分、简单发型）。
   推荐 A 起手，B 作为 Stage 1 后的可选升级。
2. **默认视角**：桌面端默认 2D 还是 3D？推荐默认 2D、3D 做开关，
   等 3D 在真机上验证稳了再考虑默认 3D。
3. **机位**：侧面电视转播角是否满意，还是想要底线后方（篮筐后）的视角？
4. **名字牌**：3D 里球员头顶是否保留名字 + 实时得分牌（推荐保留，
   与 2D 的 `tok-name` / `tok-pts` 一致）？
5. **扣篮闪光**：3D 扣篮动画播出时，是否同时保留现有的 `showDunkFlash`
   闪光（推荐保留做强调，3D 关掉时它仍是唯一提示）？
6. **性能底线**：必须跑顺的最低机型是哪一档（例如 iPhone 12 / 骁龙 778G
   级别）？这决定 Stage 5 的优化力度。

## 9. 工作量感觉与风险（实话）

### 工作量（相对大小，不承诺绝对工期）

- **Stage 1 是最大的一块**（约占一半）：场景、模型生成、快照驱动、
  渲染循环全在这里；它是地基，错了后面全返工。
- **Stage 3 是第二大块**：动画本身不难，难的是时序策略（第 6 节）和
  各种事件组合下的状态收敛（例如投篮动画播到一半来了换人快照）。
- Stage 0 / 2 / 4 是小活；Stage 5 是中活（主要是真机测试时间）。
- 总体是一项**按会话推进的多周功能**，不是周末小改动；也不适合
  在剩余额度紧张时开工（写方案便宜，写代码贵）。

### 风险

1. **手机性能**：WebGL 在低端机和 Capacitor WebView 里是最不确定的部分；
   必须真机验证，模拟器和桌面 Chrome 通过不算数。
2. **动画 / 战报同步**：2x/3x 下的打断与压缩逻辑是 bug 高发区；
   验收时必须单测“连续三个回合事件在 200ms 内到达”这种极端情况。
3. **示意移动显假**：小人滑行而没有脚步细节时容易像“棋子在飘”；
   缓解办法是跑动摆动 + 落位微漂 + 待机呼吸（Stage 3 的循环动画），
   但不要指望它看起来像真实跑位——预期见第 1 节。
4. **Three.js 版本 pinning**：API 经常变，vendoring 后不要跟风升级；
   升级 = 单独的一次回归任务。
5. **测试边界**：WebGL 本身进不了 Node 测试。能进测试的只有纯逻辑：
   百分比 → 3D 坐标映射、开关持久化、WebGL 缺失时的回退分支、
   动画打断/压缩的状态机；画面效果只能靠真机 + 桌面浏览器人工验收。
