# 《场边传奇》长期养成与穿越生涯设计

日期：2026-10-18  
状态：已确认，待实施计划  
产品定位：历史 NBA 场边执教模拟器

## 1. 决策摘要

游戏收敛为三条产品主线：

1. **快速对战**：预算轮抽、双人竞价、传奇八队、选秀建队、多人淘汰赛、快速演示作为不同开局规则，而不是并列的大量主页入口。
2. **联盟经理**：基于现有赛季引擎扩展的长期经营沙盒，目标体验接近 Basketball GM，但保留本作的赛前布置和临场指挥。
3. **穿越生涯**：玩家以球队经理兼教练身份穿越到所选历史年份，参加面试并从三份邀约中选择球队，在五年内通过选秀、培养、交易和临场执教改写历史。

技术上选择“共享联盟生涯内核”，而不是继续在 `js/app.js` 中叠加模式分支，也不进行一次性完全重写。常规赛、联盟经理和穿越生涯共用赛季推进、球员成长、市场、比赛模拟和版本化存档。

## 2. 已确认的产品约束

- 穿越主角身份为球队经理兼教练，不是球员。
- 时间线从真实年份、真实球队和真实新秀班开始。
- 玩家干预后允许产生蝴蝶效应，交易、成长、战绩和冠军不再强制复刻史实。
- 穿越生涯首个完整版本为五年篇章。
- 故事与管理同等重要；剧情选择必须进入模拟系统产生后果。
- 开局先选年份，再参加面试，从三份差异化邀约中选择。
- 弱队通常给更高权限和更低短期目标；强队资源更好，但争冠和媒体压力更高。
- 手动选择永远覆盖自动推荐。自动阵容、对位、培养或交易建议不得静默覆盖玩家的明确选择。
- 未来知识只能提供有限优势，不能直接展示确定答案或保证结果。

## 3. 现状与问题

现有项目已经具备可复用基础：

- `js/engine/season.js`：赛程、常规赛、季后赛、奖项、多赛季推进。
- `js/engine/seasonMarket.js`：工资帽、自由球员、裁员、签约、交易、职员市场。
- `js/engine/develop.js`：按历史赛季卡阶梯推进球员生涯，缺少史实卡时使用年龄曲线。
- `js/engine/sim.js`：回合制比赛模拟和比赛中状态恢复。
- `js/data/historicalSeasons.js`、`careerArc.js`、`league.js`：历史年代、年龄阶段和联盟数据。

主要结构性问题：

- `js/app.js` 约 8,800 行，混合屏幕路由、DOM、所有模式、存档和比赛结果分发。
- 中途存档 `cls_savegame_v1` 与赛季存档 `cls_season_v1` 相互独立，前者不保存 `state.season`。
- 现有 `career` 名称指金币晋级赛，不适合继续承载新的个人生涯含义。
- 赛季 UI 与事件处理仍集中在 `app.js`，继续添加长期模式会扩大回归面。
- 历史球员成长可复用，但真实新秀入盟、乐透、合同年限、CPU 建队逻辑仍需补齐。

## 4. 目标架构

### 4.1 模块边界

新增模块采用以下边界：

- `js/core/gameStore.js`
  - 保存唯一根状态。
  - 提供 `getState`、`dispatch`、`subscribe`。
  - 只处理状态变更和事件通知，不操作 DOM。
- `js/data/saveRoot.js`
  - 保存版本化根存档。
  - 提供迁移、校验、JSON 导入、JSON 导出和多槽位能力。
  - 读取旧 `cls_savegame_v1` 与 `cls_season_v1`，迁移后仍保留旧键一段兼容期。
- `js/modes/leagueCareer.js`
  - 编排赛季开始、比赛日推进、休赛期、选秀、市场和年度结算。
  - 调用现有 `season.js`、`develop.js`、`seasonMarket.js`，不复制其算法。
- `js/modes/franchiseMode.js`
  - 联盟经理入口规则、目标和 UI 状态。
- `js/modes/timeTravelCareer.js`
  - 穿越生涯的年份选择、面试、任务、故事变量、事件与结局。
- `js/story/eventEngine.js`
  - 根据条件筛选事件，应用选择效果，写入时间线。
  - 事件数据与执行逻辑分离。
- `js/story/events/*.js`
  - 序章、选秀、球队、球员关系、媒体、伤病、季后赛和结局事件。
- `js/ui/seasonHub.js`
  - 赛季主页与标签页 UI。
  - 通过回调进入共享比赛流程，不直接拥有模拟引擎。

第一阶段不要求立刻拆完整个 `app.js`。只抽出长期玩法需要的赛季编排与存档边界，其他模式保持兼容。

### 4.2 依赖方向

依赖必须单向：

`模式/UI → 生涯控制器 → 现有纯引擎 → 数据`

`saveRoot` 可序列化根状态，但不能依赖具体 DOM。`eventEngine` 可以发出领域事件，不能直接切换页面。`app.js` 在迁移期作为组合根，负责连接 UI、控制器和共享比赛入口。

## 5. 联盟经理养成循环

一个完整年份由以下阶段组成：

1. **休赛期开局**：老板目标、预算、职员、球队需求。
2. **选秀准备**：球探报告、试训、未来知识线索、选秀承诺。
3. **选秀与签约**：真实年代新秀班、乐透、顺位、交易选秀权、新秀合同。
4. **训练营**：选择个人训练、角色、导师和负荷。
5. **常规赛**：可模拟、打关键比赛或完整临场执教。
6. **动态事件**：关系、媒体、伤病、士气、承诺和球队文化。
7. **季后赛与评奖**：荣誉、老板评价和故事节点。
8. **年度结算**：成长、衰退、合同、退役、履历和联盟历史。

球员成长不只由固定历史卡决定。下一年史实卡作为基础轨迹，训练质量、角色稳定、上场时间、导师、伤病和士气提供受限修正。修正不能无限叠加，也不能让普通培养完全覆盖天赋差异。

## 6. 穿越生涯设计

### 6.1 开局

玩家选择：

- 穿越年份。
- 管理理念：重视数据、球员关系、战术创新或传统球探。
- 背景优势与弱点，用于面试和初始关系。

系统从当年联盟生成三份邀约：

- 重建队：权限高、资源少、容错较高。
- 中游队：阵容问题明确，需要在限定时间进入季后赛。
- 强队或豪门：资源和球星更好，但短期目标、媒体压力和更衣室政治更高。

每份邀约必须展示球队需求、老板目标、可用权限、核心矛盾和第一年承诺，不能只显示能力评分。

### 6.2 未来知识

`futureKnowledge` 是有限资源，按赛季补充少量点数。可用于：

- 识别一名潜在低顺位新秀或高风险热门。
- 提前采用训练、医疗、空间理念或投射趋势。
- 对交易对象、伤病风险或规则变化提出预警。
- 在关键剧情中说服管理层。

每次使用都产生代价：

- 增加时间线偏离度。
- 若证据不足，降低媒体或管理层信任。
- 公开预测越精确，后续事件越可能出现质疑、调查或竞争对手模仿。

游戏不直接显示“此人未来 OVR 96”。信息应以球探叙事、风险区间和证据呈现，最终结果受选择、球队环境和随机性影响。

### 6.3 持续变量

- **管理层信任**：决定选秀、交易、培养和用人权限。
- **媒体压力**：影响事件频率、老板耐心和球员舆论。
- **未来知识**：稀缺干预资源。
- **时间线偏离度**：决定史实事件是否仍会发生及其变体。
- **关系**：老板、总经理、教练组、核心球员、经纪人、媒体分别记录。
- **承诺**：面试、续约、球员沟通和媒体表态产生可追踪承诺。

这些变量必须作用于规则，不做纯装饰数值。

### 6.4 五年故事弧

- **序章**：穿越、证明身份、参加面试、签下第一份合同。
- **第一年**：建立威信，第一次用未来知识影响选秀或培养。
- **第二年**：球队风格成形，处理更衣室、交易与承诺冲突。
- **第三年**：蝴蝶效应扩大，历史对手和联盟格局开始改变。
- **第四年**：进入争冠窗口，在伤病、合同、忠诚与现实之间取舍。
- **第五年**：最终争冠和职业去留，结算王朝、功亏一篑、下课或转投其他球队等结局。

每个赛季至少包含：

- 一个管理层主线事件。
- 一个核心球员关系事件。
- 一个选秀或培养决定。
- 一个与年代背景相关的事件。
- 一个赛季结算故事。

### 6.5 结局与荣誉

结局由战绩、冠军、个人奖项、老板目标、承诺兑现、球队文化和关系共同决定。输出内容包括：

- 五年履历与主要荣誉。
- 关键选择及后果。
- 被改写的选秀、交易和冠军历史。
- 代表球员的成长轨迹。
- 主角去向和球队后续。
- 可分享的“平行历史”结果卡。

## 7. UI 收敛

### 7.1 主页

首屏只强调三条主线：

- 快速对战
- 联盟经理
- 穿越生涯

旧模式不删除，移入“快速对战”的规则选择页。旧存档继续从主页存档条恢复。

### 7.2 联盟主页

使用稳定的三段结构：

- 顶部：日期、战绩、工资、信任、当前目标。
- 主区：下一场比赛、关键任务、新闻和待办决策。
- 标签页：阵容、赛程、交易、选秀、培养、联盟、历史。

高级数值默认折叠；新手模式显示解释和推荐，进阶模式显示完整工资、倾向和细分数据。

### 7.3 比赛教练面板

收敛为四个标签：

- 战术
- 人员
- 防守
- 技能

手动对位、首发、角色、目标分钟和技能安装必须保留显式“手动”标记。任何自动整理操作都要跳过手动项，除非玩家明确选择“全部重置”。

## 8. 存档与迁移

新根存档使用独立键和显式版本号。第一阶段规则：

1. 读取新根存档。
2. 若不存在，则探测旧 `cls_savegame_v1` 和 `cls_season_v1`。
3. 将可迁移数据包装到新结构并记录来源版本。
4. 完成一次成功保存前不删除旧键。
5. 迁移失败时保留旧档并展示可恢复错误，不得写入半成品覆盖。

JSON 导出文件包含：

- schema 版本。
- 导出时间。
- 游戏版本。
- 根状态。
- 校验摘要。

导入先解析和迁移，再让玩家确认槽位。未知的新版本存档必须拒绝导入并解释原因。

## 9. 错误处理与容量

- 存档写入使用“序列化校验 → 写临时键 → 回读校验 → 替换正式键”的两阶段流程。
- `localStorage` 配额不足时，优先裁剪旧比赛逐回合日志和冗余 box score，不裁剪当前赛季核心状态、手动设置或故事决定。
- 事件应用必须是原子的：条件不满足或效果失败时，不消耗未来知识，也不写入半条时间线。
- 找不到历史新秀班时，使用年代匹配的生成新秀并在 UI 标记为架空球员。
- 旧存档中的未知技能或球员字段应忽略并保留可识别数据，避免整档失效。

## 10. 测试策略

### 10.1 Node 冒烟测试

- 旧中途存档迁移。
- 旧赛季存档迁移。
- 新存档导出后导入等价。
- 未知新版本被安全拒绝。
- 赛季推进一年后年份、赛程、合同与成长同时更新。
- 同一随机种子生成稳定的面试邀约和事件候选。
- 未来知识事件成功、失败和回滚。
- 手动阵容、对位、培养计划不会被自动推荐覆盖。

### 10.2 浏览器流程测试

- 从主页进入穿越生涯，选择年份，完成面试并创建存档。
- 退出浏览器后恢复到同一待决策节点。
- 从联盟主页进入比赛，完成比赛后正确回到赛季并记录结果。
- 导出存档、清空本地数据、导入后继续。
- 旧常规赛与金币晋级赛仍可开始和恢复。

### 10.3 视觉回归

固定截图覆盖：

- 三主线主页。
- 联盟主页。
- 面试三邀约。
- 选秀与培养页。
- 比赛四标签教练面板。
- 五年结局与平行历史卡。

## 11. 分阶段交付

### 阶段 1：共享地基

- 新建根状态与订阅。
- 新建版本化根存档、迁移、导入导出。
- 抽出赛季编排控制器和最小赛季 UI 边界。
- 建立 Node 冒烟测试。
- 保持现有模式行为兼容。

完成标准：旧常规赛仍可玩；新模式可以从同一联盟内核创建、保存和恢复；手动选择不被自动逻辑覆盖。

### 阶段 2：联盟经理

- 真实年代新秀班、乐透、选秀权和新秀合同。
- 训练、角色、导师、士气和伤病对成长的修正。
- CPU 阵容需求、交易和选秀决策。
- 多赛季履历、球队历史和联盟时间线。

完成标准：可连续经营至少十五年，联盟状态持续演化且不依赖预设剧情。

### 阶段 3：穿越生涯

- 年份、背景和理念创建。
- 面试与三份邀约。
- 故事事件引擎和持续变量。
- 五年主线、年代事件、多个结局。
- 平行历史分享卡。

完成标准：从序章到第五年结局完整可玩，选择会同时改变故事和模拟结果。

### 阶段 4：收敛与打磨

- 主页三主线和旧入口归并。
- 比赛教练面板四标签。
- 赛后执教复盘与关键时刻介入。
- 新手 / 进阶信息层级。
- 全关键流程和视觉回归测试。

## 12. 第一实施切片

第一实施切片严格限定为：

1. 新根存档及两类旧存档迁移。
2. JSON 导入与导出。
3. `leagueCareer` 控制器包裹现有 season state。
4. 穿越生涯创建状态：
   - 选择历史年份。
   - 生成三份差异化球队邀约。
   - 选择邀约后创建第一赛季。
5. 序章故事：
   - 一次面试决定。
   - 一次未来知识决定。
   - 信任、知识和时间线记录发生变化。
6. 对以上行为建立 Node 冒烟测试。

此切片不包含完整合同重做、完整选秀权交易、五年全部事件或最终主页重构。它的目的不是做演示壳，而是建立后续所有长期玩法都能继续使用的真实数据与控制边界。

## 13. 非目标

- 第一阶段不做联网账号、云存档或在线多人。
- 不在第一阶段完全重写 `GameSim`、球员数据库或所有旧模式。
- 不保证每个历史年份完全复刻当年的每笔交易和伤病。
- 不直接内置未经授权的商业音乐。
- 商业发布前必须单独评估 NBA、球队、球员姓名、照片和标识的授权风险。
