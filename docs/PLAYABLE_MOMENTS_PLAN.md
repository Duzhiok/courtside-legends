# 上手打的回合方案（DRAFT 草稿，只规划，不写代码）

> 状态：草稿，未实施。写于 2026-10-28。只规划，不动游戏代码；
> 实施前由 Luna review，并由用户确认第 10 节的开放问题。
> 游戏本体：场边传奇 · Courtside Legends（纯静态网页游戏）。
> 方向已定（用户 2026-10-28）：不搬到 Godot、不另做动作游戏，
> 在现有网页游戏里加玩法层；3D 播报（`docs/3D_BROADCAST_PLAN.md`）是
> 另一条表现层升级，两者不冲突，且可以组合（见第 1 节末）。

---

## 0. 一句话

在模拟比赛的关键时刻，把**一次出手的命中判定**短暂地交到玩家手里：
一个投篮时机条，点得准命中率加一点，点歪减一点，超时或挂机则按原
概率结算。**能力值仍是主角，玩家的输入只是一个封顶的修正**。

---

## 1. 核心定位：玩法层，不是重写；而且和 3D 播报的方向正好相反

- **3D 播报只读结果**：模拟结算完、事件 emit 出来之后，3D 视图负责
  把结果演出来。它可以在结算流程之外独立存在。
- **上手回合必须拦截结算**：玩家的输入要在“进还是不进”决定**之前**
  到达，否则修正无处可加。所以它不能只挂在事件上，必须在投篮结算
  流程里动一次手术——这是整个方案最关键、也最危险的区别。
- **什么都不动**：卡牌数据、评分、战术系统、存档结构、模拟的其他
  逻辑全部原样。修正只发生在一次出手的掷骰之前，且只影响那一次出手。
- **和 3D 的组合**：如果两期都落地，流程是：玩家点时机条 → 修正后
  结算 → 正常 emit `score` / `miss`（带 `meta.shot`）→ 3D 播报照常播
  投篮弧线。两期互不干扰。

## 2. 现状盘点（方案的地基，全部来自实读代码）

### 2.1 投篮结算是一条同步直线，没有等待点

`js/engine/sim.js` 的 `resolvePossession()`（L607 起）里，一次跳投
的结算按这个顺序走，**全程同步，没有任何 await**：

1. 选持球人、分球（`kickToTeammate`）、定战术、算空位 `open`。
2. 时钟先扣（约 L782：`this.clock -= used`，同时 `addMinutes`、
   `tickBenchRecovery`、可能触发场上受伤）——**到触发点时，本回合的
   时钟已经花掉了**，后面绝不能再扣一次。
3. 盖帽判定（约 L1016 起）：被帽就直接 `emit("miss")`（无 meta）、
   疲劳、抢篮板、`return`。**被帽的球永远到不了时机条**——帽已经
   发生了，没什么可“救”的。
4. `calcMakeProb(...)`（约 L1047）算出 `makeP`；低欲望硬投再乘 0.82；
   招牌必进（`sigOff?.guaranteed`）直接把 `makeP` 置 1。
5. `const made = Math.random() < makeP`（约 L1060）掷骰。
6. 掷骰之后的一切：标签、招牌标记清零、犯规掷骰、进/不进分支
   （记分、统计、士气、动量、助攻、and-one 罚球、疲劳、篮板/球权
   转换）。

**拦截点只能有一个**：第 4 步结束、第 5 步掷骰之前。早了（盖帽前）
没有意义，晚了（掷骰后）修正无处可加。

### 2.2 循环的暂停/恢复机制已经存在，但要小心用

`GameSim._loop()`（L523）：`step()` → 检查 `paused` → 按
`possessionDelay()`（L508：1x 是 1100–3600ms，2x 是 300ms，
3x 是 85ms）`setTimeout` 再跑下一回合。`step()`（L544）里调
`resolvePossession()`，然后 `onTick(snapshot())`。

- `setPaused(true, reason)`（L370）：清掉 timer、发一次快照，循环停住。
- `setPaused(false)`（同上）：`running = true` 后重新 `_loop()`。
- **关键细节**：`setPaused(true)` 时如果理由是 `"quarter"` 或
  `"half"` 且托管开着，会走 `autoBreak` 自动处理节间/中场并**自己
  恢复**。所以上手回合的暂停理由必须是一个新值（例如 `"playable"`），
  绝不能复用 `"quarter"` / `"half"` / `"timeout"`，否则托管可能把它
  自动跳过。
- 另一个关键细节：`_loop()` 在 `step()` 返回后会再检查一次
  `paused`，停住就不重排 timer。所以在 `resolvePossession()` 中途
  调 `setPaused(true)` 是安全的：本回合的 `step()` 跑完后循环自然
  停住，不会多跑一个回合。
- 恢复时的**硬性顺序**：先把挂起的那次出手结算完，再
  `setPaused(false)` 重排循环。顺序反了，循环会先 `step()` 一个新
  回合，压在未结算的旧回合上面——这是必须用测试锁死的顺序（见第 8 节）。

### 2.3 罚球是另一条路，结构上就不适合 v1

`shootFts()`（L2871）是一个同步 `for` 循环：1–3 个罚球挨个
`Math.random() < baller.ft`，每次 `emit("score" / "miss")`，**没有
`meta.shot`**（`handleSimEvent` 的注释也写明了：罚球事件没有 meta，
所以从来不播弧线）。一次犯规之旅塞 1–3 个时机条，又碎又烦；
而且罚球本来命中率就高，时机条的意义也小。所以罚球**不在 v1**，
v2 再议（见第 9 节）。

### 2.4 模式：哪些能玩，哪些不能

- 直播比赛的入口是 `beginGame()`（`js/app.js` L6737），构造
  `GameSim`（`onEvent` / `onTick` / `onEnd`）后 `sim.start()`。
- **排位赛是本地 vs AI**：`startRankedMatch()`（`js/app.js` 约 L2635）
  用 `autoFillTeam("排位对手", …)` 生成 AI 对手，战绩记在本地账号
  （`rankedWins / rankedLosses`）。所以排位赛在 v1 范围内——它不是
  真人对战，没有公平性争议。
- **联机对战不在 v1**：`server/online-server.mjs` 开头就写明
  server-authoritative，客户端决策要过服务端的 `validateDecision`。
  手动修正如果要进联机，得改服务端协议和校验，复杂一个量级。
- **快速模拟不在 v1**：`_quiet` 模式（快速模拟）整场没有暂停、
  没有 UI 提示，`resolvePossession()` 里多处按 `_quiet` 分支。
  时机条只属于“坐着看直播”的比赛。

## 3. v1 范围：故意做小

| 项 | v1 | 理由 |
|---|---|---|
| 机制 | 投篮时机条，1 个 | 先验证“上手打”本身好不好玩 |
| 出手类型 | 跳投：三分 + 中距离 | 见下 |
| 篮下 | 不在 v1 | 篮下是终结（扣篮/上篮/补篮），带身体接触、犯规、and-one、补篮链，时机条在主题上不对（时机是投篮手感，不是扛着人打进），且后续分支最复杂 |
| 扣篮 | 不在 v1 | 扣篮是篮下终结的一种高光事件，已有 `dunk` 事件 + `showDunkFlash`；不在 v1 里另起提示 |
| 罚球 | 不在 v1 | 见 2.3：同步循环 + 无 meta + 一趟多次，结构上不适合 |
| 模式 | 单机直播：生涯、自定义对战、排位赛（vs AI） | 都走 `beginGame()` 的直播路径；赛季征程/联盟经理的比赛若走同一路径则自动包含，**实施时先确认它们的比赛是否经 `beginGame()`**，不是则 v1 排除 |
| 联机对战 | 不在 v1 | 服务端权威，见 2.4 |
| 快速模拟 | 不在 v1 | `_quiet` 模式没有 UI 提示的位置 |

## 4. 触发条件：只在关键时刻，且全部条件同时成立

一场比赛约上百个回合（每回合约 14 秒比赛时间，`_lastPossessionSec`
默认 14），每个出手都上手会变成点按马拉松。所以触发条件是**全
部同时成立**才弹条，缺一不可：

1. 直播比赛（非 `_quiet` 快速模拟），且“手动时刻”开关开着。
2. 比赛模式在 v1 范围内（见第 3 节），且不是联机对战。
3. 进攻方是你（`off === this.you()`）。对方出手永远不弹——你不能
   替对手投，也不能替对手投丢。
4. 出手是跳投：`shot.zone` 是 `three` 或 `mid`。
5. 不是补篮（`putbackId` 路径的二次进攻）：补篮是篮板后的 scramble，
   不是一次 set shot，主题不对，且会和篮板流程纠缠。
6. 不是招牌必进（`sigOff?.guaranteed`）：必进的球没有修正的意义，
   也不该被一个条子“否决”。
7. 已过盖帽判定（结构保证，见 2.1 第 3 步）：被帽的球不弹条。
8. 关键时刻：复用代码库已有的关键时刻定义——`maybeCpuManage()`
   （`sim.js` L1512）里就是 `quarter >= 4 && clock < 120 &&
   |deficit| <= 6`。v1 直接沿用：**第四节（或加时）+ 剩不到 2 分钟 +
   分差 6 分以内**。不要在 v1 里发明第二套“关键”定义。
9. 球星/大心脏：`baller.scoring >= 82` 或 `baller.clutch >= 70`
   （阈值是提议值，实施时可调）。关键时刻 + 普通球员的出手不弹——
   保留给真正配得上“交给你”的那个人。
10. 单场上限 3 次（安全阀）：即使前面条件全中，一场比赛最多弹 3 次。

**频率测算**：关键窗口是 120 秒比赛时间，约 8–9 个回合/方，其中
你方出手约 4–5 次，再过球星/大心脏一筛，自然只剩 1–3 次。也就是说，
即使没有第 10 条，上限本身也不高；第 10 条只是兜底。

## 5. 修正公式：能力值主导，输入只是封顶的修正

### 5.1 档位（提议值，实施时可调）

| 玩家表现 | 修正 `delta` |
|---|---|
| 完美（指针落在内圈完美区） | `+0.05` |
| 良好（落在绿色区） | `+0.02` |
| 早了 / 晚了（落在绿色区外） | `-0.03` |
| 超时未点 | `0`（按原概率结算，见第 7 节） |

最终判定：`made = Math.random() < clamp(makeP + delta, 0.05, 0.95)`。

### 5.2 为什么这个公式防刷

- **修正加在 `calcMakeProb` 返回之后、掷骰之前**，不进
  `calcMakeProb` 本体。这样快速模拟、联机、AI 比赛走的都是原公式，
  修正只存在于“玩家点了条子的那一次出手”里，**从构造上就不可能
  污染其他路径**。
- 修正发生在分区上限（三分 0.45、中距离 0.52、篮下 0.68，见
  `calcMakeProb` 末尾）和 `paintCrowdPenalty`（上限之后再扣）**之后**。
  也就是说，一次完美时机的三分最多到 `0.45 + 0.05 = 0.50`——比平时
  的联赛环境上限高一点，但只发生在玩家亲手打的关键球上，且一年
  也就几次。这是故意的：关键球的手感本来就该允许超过平均值。
  但上限仍在：`clamp(..., 0.95)` 保证永远没有 100%，`0.05` 下限保证
  再歪也不归零。
- **防刷的算术**：最大修正 0.05，小于好射手和差射手之间常见的
  `makeP` 差距（0.10 以上）。一个 `makeP` 约 0.30 的差射手，完美
  也就到 0.35，仍然明显低于好射手平时的 0.45。**完美时机永远不能
  让差射手反超好射手**——这是必须用属性测试锁死的规则（见第 8 节）。
- 低欲望硬投的 0.82 折扣、招牌加成（`sigMakeBoost`）都已经算进
  `makeP` 里，修正和它们是加法叠加，不互相干扰。

### 5.3 完美区宽度：v1 固定，不随能力值缩放

两种方案的取舍：

- **固定宽度（v1 推荐）**：所有人同一个条、同一个完美区，纯考反应。
  能力值已经在 `makeP` 里占了主导，再用能力值放宽完美区等于
  双重计分——球星既有高基础命中率、又有更宽的完美区。
- **随能力值缩放（v2 实验）**：例如用 `three` / `mid` /
  `catchShoot` 把完美区放宽一点，主题是“射手手感更稳”。但会让
  公式更难解释、更难测，且有双重计分之嫌。

v1 选固定宽度，理由就一条：**规则必须能一句话讲清**——“条子对所有人
一样，球星赢在基础命中率上”。大心脏（`clutch`）放宽完美区也是
同一个道理，v2 再议。

### 5.4 超时 = 0 的设计含义（不是漏洞）

超时不扣分，意味着“不确定就等超时”是一种合法策略：等于放弃
这次修正机会，代价是 6 秒等待 + 失去加分可能。这是可以接受的——
它等价于“拒绝这次手动时刻”，而拒绝本身不该受罚。真正会被扣分
的只有“点了但点歪”，也就是主动尝试且失败。这一点要在玩家提示
里写清楚，避免玩家以为超时有隐藏惩罚。

## 6. 时机条 UI 设计

- **形态**：横条 + 左右来回摆动的指针（ping-pong，不是单向扫过，
  这样玩家可以等指针回到绿区再点，而不是一次过就没了）。
  中央是绿色区，绿色区正中是一小段完美区（颜色更亮/更窄）。
- **操作**：手机上点条子任意位置；桌面点条子、按空格、按回车都算。
  指针摆动周期约 1.2–1.5 秒（提议值），保证 6 秒超时内至少能看
  3–4 个来回。
- **位置**：盖在球场面板的上方（眼睛本来就在看球场的地方），不要
  盖住暂停/速度按钮和教练席的操作区。条子出现时球场画面定格在
  出手前的站位（循环已暂停，画面本来就是静的）。
- **反馈**：点完立即在条子上方出一行字——`完美！+5%` /
  `漂亮 +2%` / `早了 −3%` / `晚了 −3%`，然后正常走进/不进的战报
  和比分更新。**不要在结果上再叠加第二层动画**，战报本身就是反馈。
  超时则显示一行小字：`超时，按原概率结算`，然后同样正常结算。
- **开关**：教练席放一个“手动时刻：开 / 关”切换，状态存
  `localStorage`（例如 `courtside-playable-moments`），刷新后保持。
  默认值推荐**开**（单机直播比赛）：这是玩家要的功能，默认关等于
  藏起来；但开关必须一眼能找到，第一次触发时给一句提示
  （“关键球交给你了，指针到绿区时点一下”）。

## 7. 暂停 / 超时设计（最危险的部分，多说几句）

### 7.1 挂起-恢复的正确顺序（硬性规则）

1. 触发点（盖帽判定通过、`makeP` 已算出、掷骰之前）：把一次
   出手所需的全部上下文装进一个**挂起对象**——`baller`、`defender`、
   `shot`、`open`、`off`、`def`、`plan`、`sideCtx`（scheme、kickedOut、
   organizerId）、`makeP`、以及 `fatOpts` 闭包的输入值
   （hunt、defPress、offShare、organizerId、scheme、tempoId——
   **存输入值，不存闭包**，因为恢复时要在同一个函数作用域外重建
   疲劳调用）。
2. `setPaused(true, "playable")`：清 timer、发快照，循环停住。
   理由必须是 `"playable"`，不能是 `"quarter"` / `"half"` /
   `"timeout"`（见 2.2：托管会自动跳过前两种）。
3. UI 弹条、起 6 秒超时计时（见 7.2）。
4. 玩家点了 → `delta` 按第 5 节算出；超时 → `delta = 0`。
5. **先结算，再恢复**：调一个新的恢复方法（例如
   `sim.resolvePendingShot(delta)`），它内部用
   `made = Math.random() < clamp(makeP + delta, 0.05, 0.95)` 掷骰，
   然后走**同一套**掷骰后分支（标签、犯规、进/不进、统计、士气、
   动量、疲劳、篮板/球权转换）——**绝不复制第二套进/不进分支**。
   正常路径和手动路径共用掷骰后代码，只是 `made` 的来源不同。
6. 最后 `setPaused(false)` 重排循环，下一回合正常开始。

**为什么必须抽出“掷骰后分支”**：如果手动路径复制一份进/不进
分支，之后任何一次结算逻辑改动（统计、士气、and-one）都要改两处，
必然会漏。抽成一个方法、两个调用点，是唯一可维护的形状。

### 7.2 超时：6 秒，只有一个结果

- 超时计时是 UI 层的墙钟 `setTimeout`（约 6 秒，提议值），点中即清。
- 超时 → `delta = 0`，走第 7.1 步的正常结算。**不扣分、不加分、
  不重掷、不卡住**。
- 兜底链（按优先级）：① 点中清计时；② 超时按 0 结算；③ 条子组件
  卸载/报错时 `catch` 里按 0 结算。**任何一条路都必须落到结算**，
  不存在“等不到输入”的状态。

### 7.3 速度、挂机、切后台、换人、存档

- **2x / 3x**：提示本身就是暂停，速度在提示期间没有意义；恢复后
  按玩家当前选的速度继续。**不需要“提示时强制降回 1x”**，暂停
  已经覆盖了这个问题。2x/3x 下的关键球照常弹条（只是弹得更突然，
  因为回合间隔只有 300ms / 85ms——这是可以接受的：关键球本来就
  值得打断）。
- **挂机**：玩家一个都不点，每次提示 6 秒超时按原概率结算，比赛
  照常打完，只是慢一点。**挂机玩家必须能打完一整场**，这是验收
  清单的第一条（见第 8 节）。
- **切后台 / 切标签页**：浏览器会节流后台 timer，6 秒超时在后台
  可能拖长，但最终一定会触发；不存在死锁。切回来时要么条子还在
  （可以继续点），要么已经超时结算。**不要**为切后台加 visibility
  特殊逻辑——节流只是变慢，不是停住。
- **提示期间换人/调战术**：教练席在提示期间保持可用（和暂停时
  一致）。换人不影响挂起的出手：结算用的是挂起时存的 `baller`
  引用和 `makeP`，球员对象即使被换下也仍然有效；战术调整只影响
  后面的回合，不影响已经算好的这次 `makeP`。**提示计时不因教练
  操作延长**。
- **手动暂停/速度按钮在提示期间**：忽略或禁用。提示本身就是暂停，
  再按暂停没有意义；速度在恢复后生效。
- **存档**：提示期间**禁用存档按钮**（一行 UI 守卫）。理由：挂起
  对象是瞬时的，**不进 `exportState()`**；如果允许在提示期间存档，
  恢复时会丢掉挂起状态，等于无声地吞掉一次出手。禁掉存档后，
  重载行为和今天完全一样：从上一个存档点继续，提示消失，不产生
  新的危险。实施时顺带确认：没有 unload 时的自动存档会撞上提示
  状态；如果有，先修它，再上本功能。

### 7.4 不变量（测试要锁死的）

- 同一时间最多存在一个挂起提示（循环停住了，不可能再 `step()` 出
  第二个——这是结构保证，不是约定）。
- 任何提示都有且仅有一条出路：点中、超时、组件异常——全部落到
  结算。
- 结算顺序永远是“先结算、后恢复”，恢复后循环从下一回合开始，
  不存在“旧回合结算两次”或“新回合压在旧回合上”。

## 11. 工作量感觉与风险（实话）

### 工作量（相对大小，不承诺绝对工期）

- **挂起-恢复手术是最大、最危险的一块**：抽“掷骰后分支”、挂起
  对象、恢复顺序、托管 autoBreak 的理由隔离、存档守卫——全是
  “错一点就 corrupt 一场比赛”的地方。它比条子 UI 本身大得多。
- 条子 UI 是小活：一个 div + 指针摆动 + 计时，1–2 个会话能做完。
- 触发谓词和修正公式是纯函数，单测好写，是最便宜的部分。
- 总体是一项**按会话推进的中等功能**，不是周末小改动；但比
  3D 播报小——因为它不碰渲染，只碰一次出手的流程。

### 风险

1. **死锁 / 状态 corrupt**：恢复顺序错了、提示期间存档了、异常
   没兜底——都可能让一场比赛卡住或结算两次。缓解：7.4 的不变量
   全部写成测试；超时和异常兜底链缺一不可。
2. **平衡漂移**：修正长期累积会不会让“会点条子的玩家”系统性
   占优？缓解：修正封顶 + 只在关键时刻 + 单场上限 + 防刷属性测试。
   上线后应观察：开着开关的玩家在关键球上的命中率 vs 关掉的玩家，
   差距应收敛在修正幅度的量级里。
3. **节奏打断**：关键球弹条会不会让“坐着看”的玩家觉得烦？
   缓解：只在关键时刻 + 单场上限 + 开关一眼能找到 + 第一次提示
   有文案。实在不喜欢，一键关掉就回到今天的体验。
4. **与 3D 播报的交互**：两期都落地时，手动结算的出手同样 emit
   `meta.shot`，3D 弧线照常播——这是设计好的组合，不是冲突。
   但如果 3D 先落地、手动后落地，手动期要回归 3D 弧线在“修正后
   结算”下仍然正常（它只读 emit，应该没问题，仍需回归一次）。
5. **托管冲突**：`setPaused(true, "playable")` 必须确认不触发托管
   autoBreak（理由隔离），且提示期间托管的 `managedDefense` /
   `managedCoach` tick 不会抢跑——它们只在 `step()` 里跑，而循环
   是停住的，结构上安全，仍需一测。
