# AI 开发效率规则（2026-11-04 起生效）

1. **任务分级**：L1 CSS/纯视觉；L2 UI 行为+数据绑定；L3 玩法/领域逻辑；L4 GameSim/存档/鉴权/经济。
2. **范围控制**：只做被要求的功能和必要依赖；顺手发现的问题记 `docs/BACKLOG.md`，不擅自修。
3. **时间检查点**：L1 15 分钟 / L2 45 分钟 / L3 90 分钟 / L4 调查后估。超出就停下汇报（已完成/剩余/阻塞/为何需要更多时间），不静默继续。
4. **测试按风险**：L1 语法检查 + 一次视觉检查；L2 相关单测 + 一次浏览器视觉 QA；L3 定向单测+集成；L4 全量+边界+兼容+回滚。**全量回归每批上传前跑一次，不是每次小改都跑。** 几个小功能可攒一批，上传前统一测。
5. **视觉任务**以桌面+手机截图人工审阅为主，不用大量 DOM 断言替代肉眼。
6. **不为改 UI 而改 GameSim 核心**，除非证明存在数据契约缺口；身份解析用稳定的 team/player ID 或 home/away。
7. **禁止依赖随机比赛结果的断言**（"这场一定有抢断"）；单测用固定 fixture，引擎只留少量契约测试。
8. **禁止 QA 重试循环**：同一 QA 失败一次就分析原因，不重跑碰运气；外部网络（Wikimedia 等）在测试中一律拦截。
9. **完成即停**：验收标准满足就收尾，不无限打磨。每个任务汇报：改动文件、实现摘要、测试结果、视觉 QA、已知限制、大致耗时、是否超范围。

## 协作规则（2026-11-04 用户批准，长期有效）

10. **L3 及以上：先批设计，再写实现代码，不论谁做。** 设计文档一页以内：目标、不做什么、动哪些文件/数值、验收标准、回滚方式；平衡类改动必须附**固定种子的前后对比数字**。用户批准前只允许：只读调查、测量脚本、不进 main 的原型。分工解决"谁做"，管不了"做错方向"，后者靠用户过目。
11. **做完互相 review：Luna 的活 Code 看，Code 的活 Luna 看。**
   - 作者推送后在 `docs/AGENT_CHAT.md` 写一行"待 review：提交号 + 改了什么 + 没做什么"；审查者读 diff、跑相关 QA，回一行结论（通过 / 发现 N 条）。审查者只提问题，不替作者重写。
   - 条目标 ✅ 以 review 通过为准；对方暂时没回应则标"已推送 · 待 review"，**不阻塞 main**，并告知用户。
   - L1 的 review 是两分钟扫 diff；L2 起要跑对应 QA。
   - 清单全部来自真实出过的错：① `git grep -nE "^(<<<<<<<|>>>>>>>) "` 无冲突标记，且 rebase 的退出码被**检查**而不是被管道吞掉；② 改了布局/排序/样式的，要检查**被挤走的邻近元素**，不只是被改的那个；③ UI 改动数字全绿后还要看一次稳定截图；④ 完成声明与实际范围一致（部分完成不得标"已完成"）；⑤ 新断言遵守第 7 条（不针对随机结果）。
12. **分工由 Code 按复杂度决定**：小修小补、小功能默认给 Luna；大型设计、框架、复杂 feature 由 Code 做（Code 也可以做大型复杂 coding）。认领以**推送到 origin/main 为准**；`sim.js` 里战术加成/追分/托管同一时间只一个人动；每开一项新条目先 `git fetch` 并读看板。
